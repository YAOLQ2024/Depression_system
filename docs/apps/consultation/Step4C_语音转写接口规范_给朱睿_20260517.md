# Step 4C 语音转写接口规范（给朱睿）

## 1. 文档目的

这份文档只解决 `Step 4C-2 ~ Step 4C-4` 中需要朱睿提供的 `multimodal-service` 语音链路接口规范。

目标不是讨论内部模型怎么实现，而是先把主系统与 `multimodal-service` 之间的接口契约定死，让主线可以继续推进：

- `4C-2` 原始音频上传与对象存储落地
- `4C-3` ASR 转写与 turn 绑定
- `4C-4` 基于转写结果推进问诊问题项

## 2. 当前分工口径

- 主线负责人（肖惠谦）：前端录音、`gateway-service` 转发、`consultation-service` 主链推进、问诊页接线、数据库绑定
- 朱睿：`multimodal-service` 中语音转写接口、音频对象存储落地、转写结果返回
- 刘倩：其他非 EEG 模态
- 金伟：EEG 模态与脑电帽硬件

这里要特别说明：

- 语音转写虽然归 `multimodal-service` 能力范围，但当前 owner 是朱睿
- `4C-4` 的“推进到下一题/下一阶段”仍然由主线负责人负责，不在 `multimodal-service` 内部完成

## 3. 调用链要求

V1 固定为下面这条链路：

`browser -> gateway-service -> multimodal-service -> MinIO / Dolphin ASR`

约束：

- 浏览器不直接调用 `multimodal-service`
- 浏览器不直接调用 MinIO
- 浏览器不直接调用 ASR
- 主系统只通过 HTTP JSON / multipart 接口调用朱睿这边服务

## 4. 这份接口规范需要支持的业务结果

### 4.1 支持 `4C-2`

必须做到：

- 浏览器录到的一段完整回答音频能上传到后端
- `multimodal-service` 把音频落到 MinIO
- 返回稳定的 `audio_uri`

### 4.2 支持 `4C-3`

必须做到：

- 用上传后的音频调用 Dolphin ASR
- 返回最终 `transcript_text`
- 返回转写状态和必要的错误信息

### 4.3 支持 `4C-4`

必须做到：

- 主线能根据接口返回结果判断“这一题是否已经处理完成”
- 一旦处理完成，主线就能把同一轮的：
  - `question_text`
  - `audio_uri`
  - `transcript_text`
  - `response_started_at`
  - `response_completed_at`
  绑定到同一个 turn
- 主线随后调用自己的 `consultation-service` 推进到下一题

也就是说：

- `multimodal-service` 负责返回“已经可以推进”的明确信号
- 主系统负责真正推进状态机

## 5. V1 接口结论

为了让 `4C-2 ~ 4C-4` 最快落地，V1 建议先定 3 个接口：

| 接口 | 方法 | 用途 | 是否必需 |
| --- | --- | --- | --- |
| `/api/v1/multimodal/sessions` | `POST` | 创建多模态会话 | 必需 |
| `/api/v1/multimodal/sessions/{session_id}/audio-turns` | `POST` | 上传一轮回答音频，落 MinIO，并触发 ASR | 必需 |
| `/api/v1/multimodal/sessions/{session_id}/audio-turns/{audio_turn_id}` | `GET` | 查询当前音频处理结果 | 必需 |

说明：

- 现有 `docs/services/multimodal-service/api-and-data.md` 中有 `/transcriptions`
- 但从 `4C-2 ~ 4C-4` 的实际需求看，只做 `transcriptions` 不够，因为主线还需要 `audio_uri`
- 因此这里统一收口为 `audio-turns`
- 如果朱睿坚持保留 `/transcriptions`，也必须至少保证它同时返回 `audio_uri`

## 6. 接口 1：创建多模态会话

### 6.1 请求

`POST /api/v1/multimodal/sessions`

`Content-Type: application/json`

请求体：

```json
{
  "owner_service": "consultation-service",
  "owner_session_id": "consultation-session-id",
  "user_id": "user-id",
  "stage_context": {
    "stage_id": "stage-02-chief-complaint",
    "stage_label": "主诉采集",
    "stage_order": 2
  }
}
```

### 6.2 返回

```json
{
  "session_id": "mm-session-id",
  "owner_service": "consultation-service",
  "owner_session_id": "consultation-session-id",
  "status": "ready",
  "started_at": "2026-05-17T10:00:00Z",
  "updated_at": "2026-05-17T10:00:00Z"
}
```

### 6.3 主系统依赖

主系统会把：

- `consultation_session_id`
- `multimodal_session_id`

保持一一绑定，后续每一轮音频都走这个 `multimodal_session_id`。

## 7. 接口 2：提交一轮回答音频

### 7.1 请求

`POST /api/v1/multimodal/sessions/{session_id}/audio-turns`

`Content-Type: multipart/form-data`

表单字段定义：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `consultation_session_id` | `string` | 是 | 主问诊会话 id |
| `question_key` | `string` | 是 | 当前固定问题项 key |
| `prompt_key` | `string` | 是 | 与 `question_key` 同义时可保持一致 |
| `stage_id` | `string` | 是 | 当前阶段 id |
| `node_id` | `string` | 是 | 当前脚本节点 id |
| `response_started_at` | `string` | 是 | 回答窗口开始时间，ISO8601 UTC |
| `response_completed_at` | `string` | 是 | 回答窗口结束时间，ISO8601 UTC |
| `duration_ms` | `integer` | 是 | 录音时长，毫秒 |
| `mime_type` | `string` | 是 | 例如 `audio/webm` |
| `audio_file` | `binary` | 是 | 原始音频文件 |

如果主线后面先创建了 turn，也允许加：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `turn_id` | `string` | 否 | 若主线先建 turn，则直接传入 |

### 7.2 行为要求

这个接口收到音频后，朱睿这边必须完成：

1. 校验请求字段完整性
2. 把原始音频落到 MinIO
3. 生成稳定 `audio_uri`
4. 调用 Dolphin ASR
5. 产出 `transcript_text`
6. 返回该轮处理状态

### 7.3 返回字段要求

返回体至少必须包含：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `audio_turn_id` | `string` | 是 | 语音处理记录 id |
| `session_id` | `string` | 是 | 多模态会话 id |
| `consultation_session_id` | `string` | 是 | 主问诊会话 id |
| `question_key` | `string` | 是 | 当前题 key |
| `processing_status` | `string` | 是 | `uploaded` / `transcribing` / `completed` / `failed` |
| `audio_uri` | `string` | 是 | MinIO 中的可追踪 URI |
| `transcript_text` | `string \| null` | 是 | 若 ASR 完成则返回最终文本 |
| `transcript_confidence` | `number \| null` | 否 | 若 ASR 提供置信度则返回 |
| `asr_provider` | `string` | 是 | 当前固定写 `dolphin` |
| `error_code` | `string \| null` | 否 | 失败时返回 |
| `error_message` | `string \| null` | 否 | 失败时返回 |
| `response_started_at` | `string` | 是 | 原样回显 |
| `response_completed_at` | `string` | 是 | 原样回显 |
| `created_at` | `string` | 是 | 处理记录创建时间 |
| `updated_at` | `string` | 是 | 处理记录更新时间 |

### 7.5 V1 建议

V1 最好支持同步完成。

理由：

- 当前主线还在 `Step 4`
- 如果能在一次请求内直接拿到 `audio_uri + transcript_text`
- 主线就能立刻写 turn 并推进下一题
- `4C-4` 会最顺

如果做不到同步完成，也可以先异步，但必须配套接口 3。

## 8. 接口 3：查询某轮音频处理结果

### 8.1 请求

`GET /api/v1/multimodal/sessions/{session_id}/audio-turns/{audio_turn_id}`

### 8.2 返回

返回结构与接口 2 相同，只是当前状态变化为：

- `transcribing`
- `completed`
- `failed`

### 8.3 主系统使用方式

如果接口 2 没有同步返回最终 transcript，主系统就轮询这个接口。

只有当：

- `processing_status = completed`
- `audio_uri != null`
- `transcript_text != null`

主系统才认为：

- `4C-2` 已完成
- `4C-3` 已完成
- 现在可以进入 `4C-4`

## 9. 主系统如何消费朱睿这边返回结果

朱睿这边不用负责推进问诊状态机。

主系统消费逻辑固定为：

1. 浏览器录音完成
2. 主系统把音频发给 `multimodal-service`
3. `multimodal-service` 返回 `audio_uri + transcript_text + processing_status`
4. 主系统把结果写回当前题对应的 `consultation_turn`
5. 主系统调用自己的 `consultation-service` 完成本轮提交
6. `consultation-service` 推进到下一题或下一阶段

也就是说：

- `multimodal-service` 负责“处理结果”
- `consultation-service` 负责“主链推进”

## 10. `4C-4` 对朱睿接口的最小要求

为了让主线能稳定推进，朱睿这边至少要保证：

1. 同一个 `question_key` 返回结果不能混乱到别的题
2. `audio_uri` 一旦返回就必须稳定可追踪
3. `transcript_text` 返回后不能再随意改字段名
4. `processing_status` 语义要稳定，不允许今天叫 `done`、明天叫 `success`
5. 失败时必须返回机器可判断的 `error_code`

建议固定状态枚举：

- `uploaded`
- `transcribing`
- `completed`
- `failed`

## 11. 时间字段要求

所有时间字段统一要求：

- ISO8601
- UTC
- 例如 `2026-05-17T10:01:18Z`

至少要保留：

- `response_started_at`
- `response_completed_at`
- `created_at`
- `updated_at`

## 12. 音频要求

V1 接口最低要求支持：

- `audio/webm`
- `audio/ogg`
- `audio/wav`
- `audio/mp4`

V1 建议限制：

- 单段回答时长不超过 `60s`
- 单文件大小不超过 `25MB`

如果超限，必须返回明确错误，而不是 silent fail。

## 13. MinIO 存储要求

音频对象必须落到 MinIO。

建议路径规则：

`consultation/{consultation_session_id}/{question_key}/{audio_turn_id}.{ext}`

主系统当前只要求：

- 能拿到稳定 `audio_uri`
- 能追踪属于哪一个问诊会话、哪一道题、哪一轮音频

## 14. 错误返回要求

失败时建议统一返回：

```json
{
  "audio_turn_id": "mm-audio-turn-003",
  "session_id": "mm-session-id",
  "consultation_session_id": "consultation-session-id",
  "question_key": "chief-complaint-003",
  "processing_status": "failed",
  "audio_uri": null,
  "transcript_text": null,
  "transcript_confidence": null,
  "asr_provider": "dolphin",
  "error_code": "ASR_TIMEOUT",
  "error_message": "dolphin request timeout",
  "response_started_at": "2026-05-17T10:03:10Z",
  "response_completed_at": "2026-05-17T10:03:22Z",
  "created_at": "2026-05-17T10:03:23Z",
  "updated_at": "2026-05-17T10:03:35Z"
}
```

## 15. 非目标

这份接口规范当前不要求朱睿这边负责：

- 问诊状态机推进
- 阶段切换
- `consultation-service` 内部表更新
- 表情识别
- 姿态识别
- EEG
- 最终风险结论

## 16. 验收口径

朱睿这边接口准备完成，视为满足以下条件：

1. 主线能创建 `multimodal_session`
2. 每一道题的回答音频都能上传成功
3. 每一道题都能拿到稳定 `audio_uri`
4. 每一道题都能拿到 `transcript_text`
5. 主线能基于 `processing_status = completed` 自动继续 `4C-4`
6. 出错时主线能根据 `error_code` 做提示或重试

## 17. 需要朱睿明确回复我的 6 个点

1. 接口 2 最终路径是不是就用 `/audio-turns`
2. V1 是否支持同步返回 `audio_uri + transcript_text`
3. 如果不同步，轮询接口多久能拿到最终结果
4. `audio_uri` 的路径规则和 bucket 命名是什么
5. Dolphin ASR 的失败状态码和超时策略是什么
6. 返回字段名是否完全按这份文档固定
