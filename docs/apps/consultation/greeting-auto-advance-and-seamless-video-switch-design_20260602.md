# 咨询/量表会话自动推进与无白屏视频切换统一设计

更新时间：2026-06-02

适用仓库：`depression-system`

适用范围：

- `apps/consultation/client`
- `services/consultation-service`
- `services/assessment-service`
- `packages/workflow-resources`
- 量表题库与播放清单资源

---

## 1. 文档目标

本文把两个原本分散讨论的问题合并成一条统一设计主线：

1. `greeting-001 -> chief-complaint-001` 这类系统视频节点自动推进仍会出现数秒等待。
2. 当前咨询会话与量表会话的视频切换都存在“闪一下”或短暂空白，播放器视觉上不是常驻的。

本文目标是：

- 解释当前为什么会卡、为什么会闪
- 给出一版同时适用于咨询会话和量表会话的统一方案
- 明确哪些能力应该做成共享内核，哪些应该做成会话适配层
- 让以后在量表会话后新增若干视频节点时，仍能复用同一套方法，而不是再写一套
- 把实施步骤拆清楚，并给出每一步的完成标准

本文将作为后续逐步改代码的执行依据。

---

## 2. 统一问题定义

## 2.1 当前问题不是只发生在 `greeting-001`

`greeting-001 -> chief-complaint-001` 之所以最明显，是因为它属于：

- 当前视频播完
- 前端发起后端推进
- 后端同步推进状态机
- 会话切到可回答状态
- 首轮 turn 初始化完成
- 前端再切到下一段视频

这段等待完整暴露给用户，所以最容易被感知。

但这不是唯一问题源头。咨询会话里后续题目切换、跨阶段切换，量表会话里的：

- 阶段引导视频
- 题目视频
- 量表间切换
- 未来新增的视频说明节点

本质上都属于“视频节点切换”。只要播放器仍是单 `<video>` 重建式切换，都会存在不同程度的闪屏、空白或重挂载感。

## 2.2 咨询会话和量表会话现在是两套页面，但问题模型相同

当前至少存在两条视频播放链路：

- `ConsultationPage.tsx`
- `ScaleQuestionnairePage.tsx`

两边虽然业务语义不同，但共同点很明显：

- 都由某个“当前节点”决定视频 `uri`
- 都使用单 `<video>` 元素
- 都存在题目/阶段切换
- 都可能需要在视频结束后进入下一节点
- 都需要把“视觉无白屏”和“业务状态推进正确”同时满足

因此这次设计不能只修 `ConsultationPage`，必须抽成“统一视频节点切换框架”。

## 2.3 当前闪屏的直接根因是播放器不是常驻的

当前咨询页和量表页都使用单 `<video>`，并以视频地址或 `question_key + video_uri` 作为动态 `key`。

这会导致：

1. 当前节点变化时，React 卸载旧 `<video>`
2. 新 `<video>` 重新挂载
3. 浏览器重新建立媒体状态
4. 在新首帧 ready 前，中间就会暴露空白或闪切

所以当前“白一下”的根因不是单独某个阶段慢，而是播放器生命周期策略本身不对。

## 3. 统一设计结论

本次设计采用两个互相配合的正式方案，并要求它们同时服务于咨询会话和量表会话。

## 3.1 方案 A：视频节点推进采用“预览/预热 + 正式提交”双阶段模型

对于会导致状态推进的自动视频节点，不再使用“假 prefetch 调真实完成接口”的做法。

统一原则是：

1. 在当前视频尾声先拿到“下一节点预览结果”
2. 只做推演，不提前提交正式状态
3. 一旦知道下一节点视频资源，就立刻开始后台预热
4. 当前视频真正结束时，再做正式提交
5. 如果正式结果与预览一致，则直接无缝切换

这套方法在咨询会话中首先用于 `greeting-001` 一类系统题；在量表会话中则要作为统一能力保留，供以后出现自动推进视频节点时直接复用。

## 3.2 方案 B：视频切换改为 A/B 双视频缓冲切换

无论是咨询会话还是量表会话，播放器都改为统一共享的双缓冲组件：

1. 页面中始终保留两个绝对定位重叠的 `<video>` 层
2. 一个负责当前显示
3. 一个负责后台预加载下一段
4. 只有下一段首帧真的 ready，才切换显示层
5. 在下一段 ready 前，旧视频层始终保留在屏幕上

这样播放器视觉上是常驻的，页面不会因为 React 卸载/挂载 `<video>` 而出现白屏。

## 3.3 最终必须沉淀成“共享内核 + 会话适配器”

这次不能做成：

- 咨询页一套切换逻辑
- 量表页另一套切换逻辑
- 未来新增视频节点再补第三套逻辑

必须拆成两层：

### 共享内核

- `SeamlessVideoPlayer`
- 视频预热与首帧 ready 判定
- 前后台视频层切换
- 当前 clip / 预热 clip / ready clip / displayed clip 状态管理

### 会话适配器

- 咨询会话适配器
- 量表会话适配器
- 未来新增视频节点容器适配器

适配器负责回答：

- 当前节点是谁
- 下一节点何时可预览
- 下一节点视频 URI 从哪来
- 当前节点结束时该调用哪个正式提交动作
- 正式提交后如何校验与预览结果一致

---

## 4. 为什么这两个方案必须一起做

### 只做自动推进，不做无白屏播放器

结果会是：

- 后端状态推进可能变快
- 但前端切到下一段视频时仍会闪

### 只做无白屏播放器，不做预览推进

结果会是：

- 页面不会白一下
- 但自动视频节点结束后仍可能在旧帧上挂 4-5 秒等后端

### 只修咨询会话，不抽共享能力

结果会是：

- 咨询会话改善
- 量表会话继续闪
- 以后新增视频节点继续复制粘贴逻辑

因此必须同时解决三件事：

- 下一节点何时可知
- 下一节点如何无白屏显示
- 咨询会话与量表会话如何共享同一套机制

---

## 5. 统一目标状态

改完后的目标体验如下：

1. 咨询会话中的 `greeting-001` 尾声时，系统已提前推演好下一节点。
2. `chief-complaint-001.webm` 已在后台预热。
3. 视频真正结束时，只做正式提交与快速切换，不再裸露数秒等待。
4. 咨询会话内部题目切换无白屏。
5. 咨询会话跨阶段切换观感一致。
6. 量表会话中的阶段引导视频、题目视频、量表间切换同样无白屏。
7. 以后如果在量表结束后新增几个说明视频，也能接入同一套方法，不新增独立播放器方案。

## 6. 统一抽象：视频节点切换框架

## 6.1 视频节点定义

这里统一把“会导致视频播放或视频切换的业务单元”称为视频节点，可能包括：

- 咨询系统题视频
- 咨询可回答题的视频提示
- 量表阶段引导视频
- 量表题目视频
- 量表结束后的说明视频
- 未来任何插入式的说明/引导视频

每个视频节点至少应具备：

- `node_key`
- `video_uri`
- `video_asset_id`
- `display_text`
- `transition_mode`

其中 `transition_mode` 建议统一为：

- `auto_commit`
  说明：视频播完后需要正式提交一个“完成当前节点”的动作，再进入下一节点  
- `submit_driven`
  说明：下一节点在用户提交答案后确定  
- `local_only`
  说明：前端本地即可决定切换，不依赖后端正式提交  

## 6.2 前端共享状态模型

共享播放器与切换控制层至少要维护这些状态：

- `currentNode`
- `prefetchedNode`
- `readyNode`
- `displayedNode`
- `pendingPreview`
- `pendingCommit`
- `transitionReason`

其中：

- `currentNode` 表示业务上当前节点
- `displayedNode` 表示屏幕上当前在播的节点
- 两者短时间内可以不同步，但必须可追踪

## 6.3 前端共享能力

共享前端能力建议拆成：

### `SeamlessVideoPlayer`

职责：

- 管理 A/B 双视频层
- 管理预加载
- 通过 `loadeddata/canplay` 和 `requestVideoFrameCallback()` 判定首帧 ready
- 保证切换前后屏幕始终有视频层可见

### `useVideoNodeTransitionController`

职责：

- 管理视频节点切换状态机
- 接入不同会话适配器
- 协调 preview、preload、commit、fallback

### `session transition adapter`

职责：

- 为不同会话提供统一接口
- 把会话特定的数据结构适配给共享控制层

建议统一接口形态：

- `getCurrentNode()`
- `canPreviewNextNode(currentNode)`
- `previewNextNode(currentNode)`
- `commitCurrentNode(currentNode)`
- `deriveNextNodeFromSubmitResult(result)`

## 7. 方案 A：自动推进正式修法

## 7.1 咨询会话是第一优先落地点

咨询会话里 `greeting-001` 这类自动视频节点，会在视频结束后触发真实状态推进，因此最需要先落 `preview + commit` 双阶段模型。

## 7.2 咨询会话推荐新增接口

建议新增：

`POST /api/v1/consultations/{session_id}/question-items/{question_key}/preview-complete`

这个接口只做：

- 基于当前会话和工作流脚本推演下一节点
- 返回下一节点元数据

不做：

- 修改 `session_record.status`
- 修改 `current_question_key`
- 创建新 turn
- 持久化正式状态

## 7.3 咨询会话 `preview-complete` 返回建议

建议至少返回：

- `next_stage_id`
- `next_stage_label`
- `next_question_key`
- `next_question_order`
- `next_question_video_uri`
- `next_question_video_asset_id`
- `next_question_text`
- `next_question_subtitle_text`
- `next_status`
- `transition_mode`

## 7.4 咨询会话正式完成接口继续保留

当前已有的：

`POST /api/v1/consultations/{session_id}/question-items/{question_key}/complete`

继续保留，职责改成：

- 提交正式系统题完成动作
- 执行真实状态变更
- 校验与预览结果是否一致
- 返回正式更新后的会话

## 7.5 量表会话的统一要求

量表会话当前主要是：

- 阶段引导视频
- 题目视频
- 用户答题提交后进入下一题/下一量表

当前不少切换属于 `submit_driven` 或 `local_only`，不一定像咨询 `greeting` 一样立刻需要后端 `preview-complete` 接口。

但这次设计要求是：

- 量表会话必须接入同一个共享播放器内核
- 量表会话必须接入同一个切换控制层
- 当量表会话后续新增 `auto_commit` 视频节点时，不允许另起一套设计

因此量表会话适配器应支持：

- 直接从当前 assessment state 构造 `currentNode`
- 在答案提交返回后直接派生 `nextNode`
- 对于本地可判定的阶段引导切换，走 `local_only`
- 如果后续新增自动推进视频节点，再补 assessment 侧 `preview-next`/`preview-complete` 能力，接口契约沿用同一模式

## 8. 方案 B：无白屏视频切换正式方案

## 8.1 总体思路

新增一个跨会话共享的常驻播放器组件，例如：

`SeamlessVideoPlayer`

建议放在共享路径下，例如：

`apps/consultation/client/src/components/video/SeamlessVideoPlayer.tsx`

它内部维护两个视频层：

- `videoA`：当前前台显示
- `videoB`：后台预加载下一段

两者绝对定位重叠，尺寸、布局、裁切方式完全一致。

## 8.2 切换规则

### 当前段播放

- 当前节点视频在前台视频层播放
- 另一个视频层空闲

### 下一段预加载

- 一旦共享控制层知道 `nextNode.video_uri`
- 把它写入后台视频层
- 设置 `preload="auto"`
- 调用 `load()`

### 进入 ready 判定

后台视频层至少要经过以下两个阶段：

1. `loadeddata` 或 `canplay`
2. `requestVideoFrameCallback()` 回调确认首帧已进入渲染链路

只有在第 2 步后，才允许切换显示层。

### 显示层切换

切换时：

1. 后台视频层先执行 `play()`
2. 将后台视频层 `opacity` 切到 `1`
3. 将前台视频层 `opacity` 切到 `0`
4. 保留短暂交叠过渡
5. 切换完成后暂停旧视频层
6. 交换 A/B 角色

## 8.3 页面视觉原则

切换过程中必须满足：

1. 屏幕上始终有一个视频层可见
2. 旧视频层在新视频 ready 前不得提前移除
3. 页面不出现透明底色或空白区域
4. CSS 过渡只发生在两个视频层之间，不发生在播放器容器本身

## 8.4 当前单 `<video>` 的问题

当前至少以下两处需要纳入统一改造：

- `ConsultationPage.tsx`
- `ScaleQuestionnairePage.tsx`

它们都使用单 `<video>`，并带有会导致重建的动态 `key`。

因此正式方案中必须：

- 移除这类动态 `key`
- 把播放器从“单元素重建”改成“双元素叠层切换”
- 由共享组件统一接管，而不是各页面各写一份

## 9. 两个方案的交叉点

## 9.1 交叉点 1：下一节点视频元数据来源

无白屏切换依赖下一节点 `video_uri` 尽早可知。

这个来源在不同模式下分别是：

- `auto_commit`：来自 preview 接口
- `submit_driven`：来自提交答案后的返回结果
- `local_only`：来自前端本地状态推导

## 9.2 交叉点 2：预热时机

如果直到节点结束才知道下一节点：

- 再好的双缓冲也来不及预加载

因此：

- 咨询自动视频节点先做 preview
- 量表提交驱动节点在收到提交结果后立刻预热
- 本地引导节点在本地判定下一节点后立刻预热

## 9.3 交叉点 3：播放器状态机必须高于页面业务状态

播放器不应只关心“当前题是谁”，还应显式区分：

- `currentNode`
- `prefetchedNode`
- `readyNode`
- `displayedNode`

这些状态要和：

- 咨询会话状态
- 量表会话状态
- 节点类型
- preview / submit / commit 结果

一起协同运作。

## 10. 推荐实施步骤

下面按建议顺序实施。每一步完成后都能独立验证，避免一把改太多。

## Step 1：收口统一抽象与改造边界

### 目标

先把这次改造从“修某一页”收口成“统一视频节点框架”。

### 改动内容

1. 明确共享能力边界：
   - 共享播放器
   - 共享切换控制层
   - 咨询会话适配器
   - 量表会话适配器
2. 盘点当前视频节点来源：
   - 咨询系统题
   - 咨询普通题视频
   - 量表阶段引导视频
   - 量表题目视频
3. 定义统一 `VideoNode` 数据结构与 `transition_mode`

### 完成标准

- 文档与代码注释中已经统一使用 `VideoNode` 术语
- 咨询页和量表页的现有视频节点都能映射到统一抽象
- 后续开发不再以“某页面专用视频逻辑”命名新增能力

## Step 2：先做共享 `SeamlessVideoPlayer`

### 目标

把“无白屏播放器壳”先独立出来，让咨询页和量表页都能接。

### 改动内容

1. 新增共享播放器组件
2. 内部维护 A/B 双视频层
3. 支持：
   - 当前段播放
   - 下一段预加载
   - 首帧 ready 检测
   - 显示层切换
4. 保证组件外层容器常驻

### 完成标准

- 播放器容器不因节点变化而重新挂载
- 用静态假数据也能完成 A/B 双层无白屏切换
- `ConsultationPage` 和 `ScaleQuestionnairePage` 都可以在下一步接入它

## Step 3：实现共享 `useVideoNodeTransitionController`

### 目标

让播放器切换时序和业务状态推进解耦。

### 改动内容

1. 新增共享控制 hook 或 controller
2. 统一管理：
   - `currentNode`
   - `prefetchedNode`
   - `readyNode`
   - `displayedNode`
   - `pendingPreview`
   - `pendingCommit`
3. 定义 session adapter 接口

### 完成标准

- 切换控制逻辑不再写死在某个页面组件里
- 咨询和量表都能通过适配器接入同一控制层
- 控制层可以脱离具体页面做单元测试

## Step 4：咨询会话落 `preview-complete`

### 目标

先解决 `greeting-001` 这类自动推进卡顿的根问题。

### 改动内容

1. 在 `consultation-service` 新增：
   - `POST /consultations/{session_id}/question-items/{question_key}/preview-complete`
2. 新增服务函数，例如：
   - `preview_system_question_item_completion(...)`
3. 使用临时状态快照推演下一节点，而不提交数据库
4. 返回下一节点元数据

### 完成标准

- 新接口可独立调用
- 调用后数据库状态不变化
- 返回值足够支持前端预热下一题视频

## Step 5：实现咨询会话适配器并接入共享控制层

### 目标

把咨询页从“页面内硬编码自动推进 + 单视频切换”改成“适配器 + 共享播放器”。

### 改动内容

1. 新增 consultation adapter
2. `handleVideoTimeUpdate()` 改为通过 adapter 调 preview
3. `handleVideoEnded()` 改为通过 adapter 调正式 commit
4. `ConsultationPage.tsx` 接入 `SeamlessVideoPlayer`
5. 移除当前单 `<video>` 和动态 `key`

### 完成标准

- `greeting-001` 尾声会触发 preview，不提前真实提交
- `greeting-001 -> chief-complaint-001` 等待显著缩短
- 咨询会话内部题目切换不再白屏
- 咨询会话跨阶段切换观感一致

## Step 6：实现量表会话适配器并接入共享控制层

### 目标

让量表页与咨询页共用同一播放器和切换框架。

### 改动内容

1. 新增 assessment adapter
2. 把量表阶段引导视频映射为 `local_only` 或 `submit_driven` 节点
3. 把量表题目视频映射为 `submit_driven` 节点
4. 在量表答案提交成功后，立刻将下一节点送入后台预热
5. `ScaleQuestionnairePage.tsx` 接入 `SeamlessVideoPlayer`
6. 移除量表页当前单 `<video>` 和动态 `key`

### 完成标准

- 量表阶段引导视频切换无白屏
- 量表内部题目切换无白屏
- 量表间切换观感一致
- 量表页不再维护独立的一套播放器切换逻辑

## Step 7：补齐未来扩展点与统一回退策略

### 目标

保证以后新增视频节点时不再分叉实现。

### 改动内容

1. 为共享控制层补充 fallback 规则：
   - preview 与 commit 不一致如何处理
   - 后台预热失败如何回退
   - 某节点无视频资源如何降级
2. 约定未来新增视频节点必须先映射为 `VideoNode`
3. 如果量表会话后续新增 `auto_commit` 视频节点：
   - assessment 侧按 consultation 同模式补 `preview-next`/`preview-complete` 能力
   - 前端无需重写播放器，只新增 adapter 行为

### 完成标准

- 咨询和量表两端都走同一套 fallback 原则
- 新增视频节点的需求文档可以直接引用本设计，不再另起播放器方案
- 代码结构上已经能看出“共享内核 + 会话适配器”的边界

## 12. 风险与回退策略

## 12.1 预览结果与正式结果不一致

风险：

- consultation preview 推导与真实 complete 返回不同节点

应对：

- 正式 commit 返回后始终做一致性校验
- 一旦不一致，丢弃预热结果，按正式结果重新加载

## 12.2 后台已预热，但正式状态尚未提交

风险：

- 后台已准备下一节点，但当前节点还未正式结束

应对：

- 预热只影响后台视频层，不影响当前显示层
- 当前前台视频仍保持播放直到真正结束

## 12.3 双视频占用更高内存

风险：

- 同时存在两个 `1080p` 视频层，资源占用上升

应对：

- 同时只允许一个后台预热视频
- 切换完成后立即释放旧视频层资源

## 12.4 咨询与量表又各自长回去

风险：

- 共享内核落了一半，后面又在两个页面里各写一套例外逻辑

应对：

- 新增视频切换能力必须先落到共享控制层或适配器
- 页面只允许声明节点与接线，不允许重写播放器切换时序

## 13. 最终建议

建议按下面顺序推进：

1. 先做 `Step 1`
2. 再做 `Step 2 ~ Step 3`
3. 然后做 `Step 4 ~ Step 5`
4. 再做 `Step 6`
5. 最后做 `Step 7`

这样可以保证：

- 先把“共享抽象”立住
- 再把播放器从“单视频闪切”升级成“常驻双缓冲”
- 再优先解决咨询 `greeting` 的长等待
- 再把量表会话接到同一套框架
- 最终让咨询、量表与未来新增视频节点都共享同一执行模型
