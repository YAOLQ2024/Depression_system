## 2. 当前项目定位与总体架构

根据 `README.md` 和 `docs/mcs_system_blueprint_v1.md`，MCS 不是旧版抑郁评估页面的修补，而是围绕老师确认的主流程重新设计的新系统。主链固定为：

1. 患者登录
2. 问诊准备
3. 数字人交互问诊
4. 量表问诊
5. 临床决策
6. 调节干预
7. 对话回顾与再评估
8. 如需再次筛查，再回到下一轮问诊准备

系统采用 `apps + services + packages + infra + docs` 的组织方式：

- `apps/consultation`
  - 面向患者端
- `apps/operations-console`
  - 面向管理员/研究人员
- `services/gateway-service`
  - 浏览器统一入口
- `services/identity-service`
  - 用户、会话、问诊准备字段
- `services/consultation-service`
  - 数字人问诊状态机
- `services/assessment-service`
  - 量表问诊与计分
- `services/risk-service`
  - 临床决策与风险分层
- `services/intervention-service`
  - 干预计划与执行记录
- `services/followup-service`
  - 回顾、时间线、再评估
- `services/multimodal-service`
  - 语音、表情、姿态、脑电接入与标准化
- `services/ai-service`
  - 可选 AI 扩展服务
- `packages/workflow-resources`
  - workflow、剧本、量表、风险规则、干预目录等配置资源

结论：当前系统的核心不是普通网页跳转，而是“基于状态机与资源配置的流程编排系统”。

## 3. 当前项目里“API”具体指什么

结合当前代码和文档，MCS 中的 API 应分成三层理解。

### 3.1 第一层：浏览器对外 API

这一层由 `gateway-service` 统一对外暴露，浏览器只访问网关，不直接访问后端领域服务。

作用：

- 统一鉴权
- 写入和读取 `mcs_session` cookie
- 统一错误码
- 聚合 bootstrap 配置
- 将前端请求路由到 `identity-service`、`consultation-service`、`assessment-service`

### 3.2 第二层：服务之间的内部 API

这一层是各领域服务之间的调用接口，例如：

- `gateway-service -> identity-service`
- `gateway-service -> consultation-service`
- `gateway-service -> assessment-service`
- 后续 `assessment-service -> risk-service`
- 后续 `risk-service -> intervention-service`
- 后续 `intervention-service -> followup-service`

当前内部调用有两个重要约束：

- 浏览器不直接访问领域服务
- 内部服务通过 `X-MCS-User-ID` 或 bearer token 传递已认证用户身份

### 3.3 第三层：配置/流程资源接口

MCS 不是把流程写死在代码里，而是通过配置资源驱动业务流程。严格来说，这也是系统内部的“配置化 API”。

当前配置资源包括：

- `workflow`：总阶段链路
- `interview-scripts`：数字人问诊规则脚本
- `scales`：量表题目与计分规则
- `risk-rules`：风险触发与分层规则
- `intervention-programs`：干预目录
- `doctor-personas`：数字医生配置

结论：老师要求设计的 API，不是单一的“大模型 API”，而是“前端接口 + 服务间接口 + 配置驱动接口”的整体调用体系。

## 4. 当前已经落地的 API 现状

这里必须区分“已经实现”和“文档已规划”。

### 4.1 Phase B 已落地主链

根据 `docs/architecture/phase-b-implementation.md`，当前已落地主链为：

- `apps/consultation`
  - 患者登录与注册
  - 问诊准备表单
  - 正式问诊入口占位
- `apps/operations-console`
  - 管理员/研究人员登录
  - workflow 摘要
  - doctor persona 目录摘要
- `identity-service`
  - 用户与 session
  - 问诊准备字段存储
- `gateway-service`
  - cookie 会话处理
  - identity 代理
  - workflow/bootstrap 聚合

Phase B 明确未实现：

- `consultation-service` 真实状态机执行
- 量表逐题正式联调
- 多模态采集
- 风险分层
- 干预执行
- 随访调度

### 4.2 当前已实现的网关外部接口

根据 `docs/services/gateway-service/api-and-data.md` 和当前 `services/gateway-service/app/api/*.py`，已存在的对外接口包括：

#### 认证与用户

- `POST /api/v1/auth/register`
  - 功能：患者注册
  - 请求核心字段：`account`、`password`、`full_name`
- `POST /api/v1/auth/login`
  - 功能：登录
  - 请求核心字段：`account`、`password`
  - 返回后由 gateway 将 `session_token` 写入 `mcs_session` cookie
- `POST /api/v1/auth/logout`
  - 功能：退出登录并清理 cookie
- `GET /api/v1/users/me`
  - 功能：获取当前用户
- `PUT /api/v1/users/me/profile`
  - 功能：更新问诊准备字段
  - 当前字段：
    - `full_name`
    - `age`
    - `height_cm`
    - `weight_kg`
    - `marital_status`
    - `parents_marital_status`
    - `parents_occupation`
    - `prior_psychiatric_visit`
    - `family_history`

#### 启动配置

- `GET /api/v1/catalog/doctor-personas`
  - 功能：返回数字医生配置目录
- `GET /api/v1/catalog/workflow-summary`
  - 功能：返回 workflow 摘要
- `GET /api/v1/system/bootstrap`
  - 功能：聚合前端启动所需配置
  - 当前返回两类内容：
    - `doctor_personas`
    - `workflow`

#### 问诊会话

- `POST /api/v1/consultations`
  - 功能：创建问诊会话
  - 当前浏览器请求字段：
    - `device_status`
    - `audio_channel_ready`
    - `consent_confirmed`
    - `consultation_ready_state`
- `GET /api/v1/consultations/{id}`
  - 功能：获取问诊状态
- `POST /api/v1/consultations/{id}/start`
  - 功能：启动正式问诊
- `POST /api/v1/consultations/{id}/turns`
  - 功能：提交一轮问答
  - 当前输入类型：
    - `speech`
    - `manual_input`
    - `continue_button`
    - `silence`
    - `recognition_failure`

#### 量表会话

- `GET /api/v1/assessment/catalog`
  - 功能：返回当前活跃量表目录
- `POST /api/v1/assessment/sessions`
  - 功能：创建量表会话
  - 当前网关请求字段：
    - `consultation_session_id`
    - `scale_handoff_payload`
    - `selected_scales`
    - `capture_context`
- `GET /api/v1/assessment/sessions/{id}`
  - 功能：获取量表会话状态
- `POST /api/v1/assessment/sessions/{id}/answers`
  - 功能：提交单题答案
  - 当前请求字段：
    - `item_id`
    - `selected_option_score`
    - `selected_option_label`
    - `raw_input`
    - `capture_timestamp`

### 4.3 当前接口统一规范

网关和已实现服务基本都使用统一响应包：

成功：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

错误：

```json
{
  "code": 4010,
  "message": "missing session credentials",
  "data": {}
}
```

这说明当前系统已经开始统一错误处理和前后端契约。

## 5. 当前模块之间如何协调

### 5.1 登录与启动阶段

当前已跑通链路如下：

1. 前端调用 `POST /api/v1/auth/login`
2. `gateway-service` 转发到 `identity-service`
3. `identity-service` 校验账号密码并创建 `session_token`
4. `gateway-service` 将 `session_token` 写入 `mcs_session` cookie
5. 前端调用 `GET /api/v1/users/me`
6. `gateway-service` 从 cookie 中读取 session，再向 `identity-service` 查询当前用户
7. 前端调用 `GET /api/v1/system/bootstrap`
8. `gateway-service` 从 `packages/workflow-resources` 读取 workflow 与 doctor persona 摘要
9. 前端根据 `profile_status` 决定进入问诊准备页还是后续入口页

这一阶段体现出两个协调原则：

- 浏览器永远只认 `gateway-service`
- 业务流程的启动配置来自资源文件，而不散落在前端硬编码

### 5.2 问诊准备阶段

1. 前端填写问诊准备表单
2. 调用 `PUT /api/v1/users/me/profile`
3. `gateway-service` 转发到 `identity-service`
4. `identity-service` 更新用户档案和 `profile_status`
5. 返回前端，前端进入正式问诊入口页

这里的设计说明：当前 Phase B 先把问诊准备信息暂存在 `identity-service`，后续再按文档拆成更独立的 intake/profile 结构。

### 5.3 数字人交互问诊阶段

依据 `consultation-v1.yaml` 和 `consultation-service` 文档，正式问诊不是自由聊天，而是规则驱动状态机，固定分为 4 个子模块：

1. 初始问候与流程说明
2. 主诉采集
3. 现病史规则式问诊
4. 高风险问题排查

当前会话创建与运行逻辑为：

1. 前端调用 `POST /api/v1/consultations`
2. `gateway-service` 先向 `identity-service` 取当前用户
3. `gateway-service` 拼装 `participant_profile_snapshot`
4. 网关把用户信息与设备状态一并发给 `consultation-service`
5. `consultation-service` 创建 `consultation_session`
6. 绑定 `consultation-v1` workflow
7. 绑定默认 doctor persona
8. 初始化到 `stage-01-greeting-and-briefing`
9. 前端调用 `POST /api/v1/consultations/{id}/start`
10. 服务进入 `running` 状态并自动推进到第一个等待输入节点
11. 之后每一轮由 `POST /api/v1/consultations/{id}/turns` 提交患者输入

当前 `consultation-service` 会保存这些核心状态：

- `workflow_id`
- `script_bundle`
- `current_stage_id`
- `current_node_id`
- `status`
- `assigned_doctor_persona`
- `participant_profile_snapshot`
- `slot_values`
- `chief_complaint_summary`
- `current_history_structured_result`
- `high_risk_screening_result`
- `scale_handoff_payload`

这意味着问诊服务本质上是“可回溯状态机”，不是普通消息列表。

### 5.4 高风险安全门

根据 `packages/workflow-resources/interview-scripts/rule-v1/stage-04-high-risk-screening.yaml`，高风险排查是独立安全门，而不是普通追问的一个问题。

当前配置中，高风险排查至少关注：

- 是否有自杀/自伤念头
- 是否已有计划或行为
- 当前是否存在可联系的支持者

一旦满足高风险条件：

- 标记 `requires_human_review = true`
- 暂停标准问诊流程
- 不直接继续量表阶段

这部分非常适合在汇报中强调，因为它体现了系统设计的安全优先级。

### 5.5 量表问诊阶段

根据 `assessment-service` 当前实现和文档，量表链路已经形成较清晰的接口设计。

当前活跃量表为：

- `phq9`
- `sds`
- `sas`
- `social-function`

保留但暂不启用：

- `scl90`

当前量表协同流程为：

1. 问诊服务输出 `scale_handoff_payload`
2. 前端或上游流程调用 `POST /api/v1/assessment/sessions`
3. `assessment-service` 创建 `assessment_session`
4. 读取量表 yaml 配置
5. 返回当前量表和当前题目
6. 患者逐题提交答案
7. 服务归一化答案并计分
8. 每完成一个量表立即后端落库
9. 前端不提前展示单量表结果
10. 全部量表完成后生成 `aggregate_payload`

当前 `aggregate_payload` 已包含：

- `assessment_session_id`
- `consultation_session_id`
- `scale_count`
- `scale_results`
- `source_handoff`

这部分后续就是交给 `risk-service` 的核心输入。

### 5.6 后续规划中的后链路

根据蓝图与服务文档，量表之后的标准链路是：

1. `risk-service`
  - 接收问诊结构化结果、量表聚合结果、多模态特征
  - 输出 `risk_level`、`risk_explanation`、`referral_recommendations`、`lifestyle_suggestions`、`intervention_entry_payload`
2. `intervention-service`
  - 根据风险结果生成干预计划
  - 记录干预执行与反馈
3. `followup-service`
  - 生成回顾记录、时间线、再评估任务、导出报告

因此，当前 MCS 的模块协调路线可以概括为：

`identity -> gateway -> consultation -> assessment -> risk -> intervention -> followup`

## 6. 当前项目里“大小模型协调”到底是什么状态

这一部分必须严格按项目现状来讲，不能自己想象。

### 6.1 当前结论

根据 `docs/mcs_system_blueprint_v1.md` 和 `docs/services/ai-service/tasks.md`：

- 当前主链不是 LLM 驱动主链
- 当前明确要求“先不上 LLM + RAG 主链”
- 当前正式问诊以规则树/状态机驱动
- `ai-service` 是可选扩展服务，不属于当前必须跑通的主链
- 关闭 `ai-service` 后，主链仍然必须正常工作

也就是说，当前项目并没有把“大模型回答一切”作为架构核心，而是采用：

- 规则主链保证稳定性和可控性
- AI 作为可选增强能力后置接入

### 6.2 当前项目中与“模型”相关的两个位置

#### 位置一：`multimodal-service`

它负责的是本地/专项模型能力接入，例如：

- 语音转写
- 语音情绪和声学特征
- 表情特征
- 姿态特征
- 脑电特征

这些能力更接近“小模型”或专项推理模型，它们的输出是 `feature bundle`，而不是最终临床结论。

#### 位置二：`ai-service`

它负责未来的生成式增强能力，例如：

- 问诊摘要
- 结构化抽取
- 辅助建议
- 提示词编排
- 模型适配器与审计

这更接近“大模型”扩展位，但目前文档明确要求它不能成为唯一依赖。

### 6.3 基于现有文档，可以如何表述大小模型分工

如果汇报老师问“大小模型怎么协调”，当前最符合项目文档的回答应是：

1. 规则状态机仍然是主链核心，不由大模型直接接管流程。
2. `multimodal-service` 承担语音、表情、姿态、脑电等专项推理，更适合作为小模型/专用模型层。
3. `ai-service` 作为可选生成式增强层，后续承担摘要、结构化抽取、辅助建议等大模型能力。
4. 任何单一模型输出都不能直接替代风险判断，尤其是多模态结果只能作为辅助依据。
5. 所有 AI 输出都必须可审计、可关闭、可降级。

这不是空想，而是当前 `ai-service/tasks.md` 与 `risk-rules/consultation-v1.yaml` 已明确写出的系统原则。

### 6.4 当前项目对模型协调的硬约束

根据现有文档，可以总结出 5 条硬约束：

1. 主链必须在没有 `ai-service` 的情况下仍可运行。
2. AI 输出只能作为辅助结果，不能强行绑死下游服务。
3. 多模态信号只能辅助风险分层，不能单独给出最终风险等级。
4. 高风险排查结果可以优先触发人工复核，不等待模型完整推理。
5. 模型调用必须有版本、日志、超时、降级和审计信息。

## 7. 可以直接在汇报中使用的总结表述

### 7.1 关于 API 的一句话定义

在 MCS 里，API 不只是前端访问后端的接口，还包括服务之间的内部调用接口，以及 workflow、剧本、量表、风险规则等配置资源驱动接口。

### 7.2 关于模块协调的一句话定义

MCS 采用“网关统一接入、领域服务分阶段处理、配置资源驱动流程状态机”的协同模式，核心链路为：

`登录 -> 问诊准备 -> 数字人问诊 -> 量表问诊 -> 临床决策 -> 调节干预 -> 回顾与再评估`

### 7.3 关于大小模型协调的一句话定义

当前项目不是大模型主导架构，而是“规则主链 + 多模态专项模型辅助 + 可选 AI 服务增强”的分层设计，其中大模型能力被保留为后续可审计、可降级的增强模块。

## 9. 一个 2 分钟的口头汇报版本

老师这套系统在 API 设计上，不是只考虑前端调后端，而是分成三层。第一层是浏览器通过 `gateway-service` 访问的统一外部接口，比如登录、获取当前用户、问诊会话创建、量表会话创建等。第二层是各服务之间的内部 API，例如 gateway 转发到 identity、consultation、assessment，后续 assessment 再把聚合结果交给 risk、intervention、followup。第三层是配置资源驱动接口，也就是 workflow、问诊剧本、量表、风险规则和干预目录，这些不再写死在代码里。

从模块协调上看，MCS 的主链已经固定为登录、问诊准备、数字人问诊、量表问诊、临床决策、调节干预、对话回顾与再评估。当前 Phase B 已经跑通了认证、bootstrap 和问诊准备链路，问诊服务和量表服务也已经有清晰的接口和数据结构。数字人问诊不是自由聊天，而是规则状态机，固定拆成初始问候、主诉采集、现病史追问和高风险排查四个模块，其中高风险排查是独立安全门。

关于大小模型协调，当前项目并没有把大模型作为主链核心。系统明确要求先用规则树和状态机稳定主流程，多模态服务负责语音、表情、姿态、脑电等专项模型输出，AI 服务作为后续可选增强层，用于摘要、结构化抽取和辅助建议，而且关闭 AI 服务后主链仍然必须可运行。所以当前架构的核心思想是规则主链优先，模型能力分层接入，所有 AI 输出必须可审计、可降级。
