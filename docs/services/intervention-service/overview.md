# `intervention-service` 服务设计概览

## 1. 概述

`intervention-service` 负责 MCS 中“调节干预”阶段的方案选择、执行记录与反馈接收。

它基于风险结果和干预目录，为患者生成可执行的干预计划，并记录执行情况与用户反馈。

## 2. 核心设计结论

- `intervention-service` 不负责做临床风险判断，而是消费风险结果并生成可执行方案。
- 干预方案必须配置化，从 `intervention-programs` 目录读取，不写死在代码里。
- 方案输出不仅是“推荐什么”，还必须包含执行强度、执行方式、时长和反馈入口。
- 干预执行记录是后续 `followup-service` 做回顾和再评估的重要输入，不能只保留最终结果。

## 3. 职责边界

负责：

- 读取干预方案目录
- 根据风险结果匹配调节方式
- 生成干预计划和强度建议
- 记录干预执行过程
- 接收用户反馈

不负责：

- 最终风险等级判断
- 数字人问诊和量表作答
- 回顾报告和再评估调度

## 4. 上下游

上游：

- `risk-service`
- `consultation` 应用

下游：

- `followup-service`
- `packages/workflow-resources/intervention-programs/catalog.yaml`
- 后续音频、视频、图文资源分发层

## 5. 当前实现状态

已实现：

- 只有健康检查占位
- 干预目录只有基础目录清单

待实现：

- 干预计划匹配逻辑
- 执行会话模型
- 用户反馈模型
- 下游回顾移交逻辑

已知限制：

- 当前干预目录只有基础类型和强度级别，没有适用条件和时长细则
- 没有执行资源实际分发链路
- 没有暂停、跳过、提前结束等执行状态建模

## 6. 非目标

- 不在本服务内重新计算风险等级
- 不把音视频静态资源托管逻辑和业务计划逻辑混在一起
- 不把回顾与再评估逻辑写进本服务
