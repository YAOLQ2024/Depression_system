# face / pose / live 采样与轮询调优方案

更新时间：2026-05-23

适用仓库：`depression-system`

---

## 1. 文档目标

本文档只解决一个问题：

**在不重做多模态架构的前提下，调整 `face`、`pose` 和 `live` 的前端采样/轮询频率，让链路更符合当前模型特性和联调体验。**

本文档不处理：

- 数据库结构改造
- 模型更换
- 前后端接口协议重构

---

## 2. 当前现状

当前问诊前端存在两条并行链路：

1. `live` 轮询
   - 频率：每 `2s`
   - 作用：刷新 `speech / text / face / pose` 的 session 级实时快照

2. 摄像头帧采样
   - 频率：每 `2.5s`
   - 作用：从同一张截图同时提交：
     - `face capture`
     - `pose capture`

换句话说，当前活跃问诊窗口大致会产生：

- `live`：30 次/分钟
- `face`：24 次/分钟
- `pose`：24 次/分钟

总计约 `78` 个请求/分钟/活跃用户。

---

## 3. 当前主要问题

### 3.1 `live` 刷新偏勤

`face / pose` capture 成功后，前端本地状态已经会立刻合并最新结果。

在这个前提下，`live` 继续每 `2s` 全量拉一次，收益有限，但会增加：

- 前端请求量
- 网关与 consultation-service 的读压力
- 浏览器 Network 噪音

### 3.2 `pose` 采样偏慢

当前 `pose` 模型不是纯单帧情绪识别，而是：

- 单帧图像提取 pose landmarks
- 再进入 turn 级短时窗口累积
- 至少 `8` 帧后才开始稳定推理

如果按当前 `2.5s` 一帧：

- `8` 帧大约需要 `20s`

这会直接导致：

- `pose` 长时间停留在 `collecting`
- 用户看到姿态结果出现过慢
- `pose` 模态存在感弱

### 3.3 `face` 与 `pose` 被绑成同一频率

这在工程上简单，但不符合模态特性：

- `face` 更接近单帧主导
- `pose` 更依赖短时间窗

两者使用同一采样周期，会导致一边保守、一边不够用。

---

## 4. 推荐调优方案

### 4.1 推荐目标频率

建议最终调整为：

- `live`：`4~5s`
- `face`：`2.5~3s`
- `pose`：`1~1.5s`

### 4.2 推荐原因

`live`

- 它本质上是 session 级实时快照
- 当前 capture 返回本身已会回填本地状态
- 所以不需要高频硬轮询

`face`

- 单帧已经能产出较强表情线索
- `2.5~3s` 已能兼顾实时性和请求量

`pose`

- 需要短时窗口积累
- 采样必须明显快于 `face`
- 否则窗口建立过慢，识别长期滞后

---

## 5. 最小可行改法

如果这一轮只想做低风险调整，不想立刻拆成两套视觉采样定时器，建议先做：

- `live`：`2s -> 5s`
- `face/pose` 共用采样：`2.5s -> 1.5s`

这是当前最稳的折中方案。

优点：

- 改动小
- 立刻改善 `pose` 的窗口建立速度
- 立刻减少 `live` 轮询噪音

缺点：

- `face` 会跟着 `pose` 一起提频
- 请求量仍不是最优

---

## 6. 更推荐的最终改法

下一阶段更推荐拆分成两套节奏：

- `live` 独立轮询定时器
- `face` 独立采样定时器
- `pose` 独立采样定时器

推荐值：

- `live = 5000ms`
- `face = 2500ms ~ 3000ms`
- `pose = 1000ms ~ 1250ms`

这样更符合当前项目的真实情况：

- `face` 保持轻量
- `pose` 保住时序窗口
- `live` 不再强刷

---

## 7. 风险评估

### 7.1 如果只提升 `pose` 采样，不降 `live`

风险：

- Network 仍显得很忙
- 后端读压力改善不明显

### 7.2 如果只降低 `live`，不提升 `pose`

风险：

- `pose` 仍然长时间停留在 `collecting`
- 用户体验改善有限

### 7.3 如果 `pose` 提频过高

例如直接压到 `500ms` 或更高频，风险包括：

- 请求数快速上升
- `capture / inference` 写库频率过高
- 真实环境中更容易触发浏览器与网络抖动

因此当前不建议直接把 `pose` 拉到视频级高频。

---

## 8. 推荐执行顺序

建议按两步走：

### Step 1：先做低风险折中版

- `live: 2s -> 5s`
- `face/pose: 2.5s -> 1.5s`

目的：

- 快速验证 `pose` 结果出现速度是否明显改善
- 同时减少 `live` 轮询噪音

### Step 2：再做最终拆分版

- `live` 独立
- `face` 独立
- `pose` 独立

目的：

- 真正做到按模态特性调优
- 为后续更多视觉模态扩展预留空间

---

## 9. 当前建议结论

如果只允许先做一件事，我建议优先改：

- **先把 `live` 降频**
- **同时把 `pose` 所在视觉采样链路提到至少 `1.5s`**

也就是当前最推荐的第一步是：

- `live = 5s`
- `face/pose = 1.5s`

这是一版最容易落地、最容易观察效果、也最不容易把系统带偏的调优方案。
