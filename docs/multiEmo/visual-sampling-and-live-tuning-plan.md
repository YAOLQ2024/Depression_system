# face / pose / live 采样与轮询调优方案

更新时间：2026-05-23

适用仓库：`depression-system`

---

## 1. 文档目标

本文档只解决一个问题：

**在不重做多模态架构的前提下，调整 `face`、`pose` 和 `live` 的前端采样/轮询频率，让链路更符合当前模型特性和联调体验。**

本文档不处理：

- 数据库结构改造
- 模型更换
- 前后端接口协议重构

---

## 2. 当前现状

当前问诊前端存在两条并行链路：

1. `live` 轮询
   - 频率：当前已调整为每 `5s`
   - 作用：刷新 `speech / text / face / pose` 的 session 级实时快照

2. `visual-captures` 视觉共享帧采样
   - 频率：当前已调整为每 `1.5s`
   - 作用：从同一张截图提交一次 `visual-captures`
   - 后端内部再 fan-out 到：
     - `face`
     - `pose`

换句话说，当前活跃问诊窗口大致会产生：

- `live`：12 次/分钟
- `visual-captures`：40 次/分钟

总计约 `52` 个请求/分钟/活跃用户。

---

## 3. 当前主要问题

### 3.1 `live` 刷新偏勤

`face / pose` capture 成功后，前端本地状态已经会立刻合并最新结果。

在这个前提下，`live` 继续每 `2s` 全量拉一次，收益有限，但会增加：

- 前端请求量
- 网关与 consultation-service 的读压力
- 浏览器 Network 噪音

### 3.2 `pose` 采样偏慢

当前 `pose` 模型不是纯单帧情绪识别，而是：

- 单帧图像提取 pose landmarks
- 再进入 turn 级短时窗口累积
- 至少 `8` 帧后才开始稳定推理

如果按当前 `2.5s` 一帧：

- `8` 帧大约需要 `20s`

这会直接导致：

- `pose` 长时间停留在 `collecting`
- 用户看到姿态结果出现过慢
- `pose` 模态存在感弱

### 3.3 `face` 与 `pose` 仍共享同一视觉采样频率

虽然外部主链已经收敛成一次 `visual-captures` 上传，但内部仍同时服务于：

- `face` 更接近单帧主导
- `pose` 更依赖短时间窗

因此继续使用同一采样周期，仍会导致一边保守、一边不够用。

---

## 4. 推荐调优方案

### 4.1 推荐目标频率

建议最终调整为：

- `live`：`4~5s`
- `visual-captures`：`1~1.5s`

说明：

- 在当前共享输入架构下，外部主链已经不再分开上传 `face` 和 `pose`
- 因此现阶段可直接调的只有：
  - `live`
  - `visual-captures`
- `face / pose` 更细粒度的差异化采样节奏，应放到后续视觉调度器改造阶段再做

### 4.2 推荐原因

`live`

- 它本质上是 session 级实时快照
- 当前 capture 返回本身已会回填本地状态
- 所以不需要高频硬轮询

`visual-captures`

- 需要短时窗口积累
- 当前主链必须优先照顾 `pose`
- 否则窗口建立过慢，识别长期滞后
- `face` 在共享输入主链下会被动跟随提频，但这仍是当前更划算的折中

---

## 5. 最小可行改法

如果这一轮只想做低风险调整，不想立刻拆成两套视觉采样定时器，建议先做：

- `live`：`2s -> 5s`
- `visual-captures`：`2.5s -> 1.5s`

这是当前最稳的折中方案。

优点：

- 改动小
- 立刻改善 `pose` 的窗口建立速度
- 立刻减少 `live` 轮询噪音

缺点：

- `face` 会跟着 `pose` 一起提频
- 请求量仍不是最优

---

## 6. 更推荐的最终改法

下一阶段更推荐拆分成两层节奏：

- `live` 独立轮询定时器
- `visual` 独立采样定时器
- 必要时再在视觉层内引入更细的模态调度

推荐值：

- `live = 5000ms`
- `visual-captures = 1000ms ~ 1500ms`

这样更符合当前项目的真实情况：

- `pose` 保住时序窗口
- `face` 在共享输入前提下继续复用同一张图
- `live` 不再强刷

---

## 7. 风险评估

### 7.1 如果只提升 `visual-captures`，不降 `live`

风险：

- Network 仍显得很忙
- 后端读压力改善不明显

### 7.2 如果只降低 `live`，不提升视觉采样

风险：

- `pose` 仍然长时间停留在 `collecting`
- 用户体验改善有限

### 7.3 如果 `visual-captures` 提频过高

例如直接压到 `500ms` 或更高频，风险包括：

- 请求数快速上升
- `capture / inference` 写库频率过高
- 真实环境中更容易触发浏览器与网络抖动

因此当前不建议直接把 `visual-captures` 拉到视频级高频。

---

## 8. 推荐执行顺序

建议按两步走：

### Step 1：先做低风险折中版

当前状态：**已完成（2026-05-23）**

- `live: 2s -> 5s`
- `visual-captures: 2.5s -> 1.5s`

目的：

- 快速验证 `pose` 结果出现速度是否明显改善
- 同时减少 `live` 轮询噪音

### Step 2：再做最终拆分版

- `live` 独立
- `visual` 独立
- 必要时再细分 `face / pose`

目的：

- 真正做到按模态特性调优
- 为后续更多视觉模态扩展预留空间

---

## 9. 当前建议结论

如果只允许先做一件事，我建议优先改：

- **先把 `live` 降频**
- **同时把 `pose` 所在的 `visual-captures` 链路提到至少 `1.5s`**

也就是当前最推荐的第一步是：

- `live = 5s`
- `visual-captures = 1.5s`

这是一版最容易落地、最容易观察效果、也最不容易把系统带偏的调优方案。
